# AEGIS — Query, evidence and import integrity audit

Baseline: the exact AEGIS_Final_Online_Reviewed.zip and AEGIS_Final_Windows_Reviewed.zip previously delivered. Both were extracted before editing. The research and protected source files are unchanged.

## Corrected defects

1. The local query grammar previously counted every matching row even when a `column` was specified for count/group_count. Counts now distinguish rows, populated values and distinct nonblank values. Grouped nonblank counts retain observed zero-count groups. Explicit nonblank-count phrasing is supported.
2. Standard and local Qwen group rankings previously truncated at the requested limit even when tied. The shared result includes boundary ties up to the 30-group cap and discloses the actual tie count and truncation. Scalar arithmetic no longer rounds values to six decimal places before ranking/display; population standard deviation uses Decimal arithmetic and is labelled as population standard deviation. Floating-point display is still finite-precision, not arbitrary precision.
3. Recognized monetary fields could be aggregated by the local query engine across mixed currencies even though charts blocked this. Local numeric measures, raw numeric chart axes and recognized monetary arithmetic in hosted SQL now reject mixed/missing/ambiguous currencies; no conversion is invented. This intentionally blocks some safe filtered or per-currency calculations as well. Unknown field meanings and arbitrary SQL semantics remain outside the guarantee.
4. Numeric-looking identifier columns were classified as numeric by the local schema and could be averaged or plotted as a numeric distribution by custom chart controls. Recognized identifiers are now treated as text by the local schema and hosted storage; direct numeric calculations and numeric chart axes reject them. Hosted explicit conversion of a recognized identifier via aegis_num is blocked for the tested direct pattern. Count/group/distinct remain available.
5. A precise standard question could be re-planned by local Qwen into a different measure. Exact understood requests now use the checked standard plan first, retaining Qwen planning for other supported requests. A rejected recognized measure is explained instead of presenting a fabricated number. This is a conservative deterministic decision; it is not a general semantic verifier.
6. Reversed numeric or date filter bounds previously yielded empty results rather than reporting an invalid filter. They now raise a validation error. Text comparisons require a scalar value.
7. Direct SQL arithmetic on invalid text and parenthesized direct aggregation could bypass earlier checks. The tested direct and parenthesized forms now require aegis_num; safe numeric conversions and arithmetic on numeric columns continue to work. This token-based check is not a full SQL parser or proof of intent.
8. Extreme timezone-normalization timestamps can overflow Python's date range. Such inputs now return NULL rather than raising an unhandled conversion error in the hosted julianday helper.
9. XLSX ingestion now rejects duplicate ZIP member names and malformed Boolean values and limits archive member count. Formula results saved in the workbook are explicitly described as possibly stale; formulas with absent or empty cached results are disclosed. Excel error cells are treated as blank and explicitly counted in import warnings. Formulas are never executed or recalculated. The first visible worksheet remains the imported sheet.
10. Streamlit workspace version advances to discard stale objects after this deployment.

## Tests and scope

15 added regression tests in `AEGIS_App/tests/test_query_ingestion_review.py`. Existing tests were not weakened or changed. Offline application tests: online 334 passed, Windows source 337 passed; online cloud-adapter tests: 91 passed. No skips. Linux test environment with AEGIS_OFFLINE_TEST_MODE=1. These counts are not independent live LLM evaluations. No live provider key was used. Actual Windows batch execution/first-time provisioning and deployed Streamlit rendering still require platform acceptance tests. Arbitrary question accuracy, currency/quantity semantics not encoded in the source, complex model SQL and future provider outages cannot be certified. No live procurement, real-world financial or prospective model validation claim is made.
